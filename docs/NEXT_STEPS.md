# 다음 구현 계획 — 제안, 현재 미구현

이 문서의 서버·STT·AI 흐름은 개발 방향이다. 동작하는 API나 배포된 서비스 설명이 아니다.
특정 프레임워크/클라우드/과금제를 확정하지 않으며, 현재 API 계약은 실제 연동 때 확인해야 한다.

## 1. 먼저 고정할 사용자 경험

촬영하는 화면에서 반복하는 동작은 ‘말하기 + 촬영 한 번’으로 유지한다.
실시간 STT를 붙였다는 이유로 녹음 시작/종료/확인 버튼을 사진마다 추가하지 않는다.
등록이 막히지 않게 사진/음성을 우선 로컬에 저장하고 변환·업로드는 별도 상태로 처리한다.
현재 `cloudStatus: not_connected`를 실제 업로드 완료처럼 표시해서는 안 된다.

## 2. 1단계: 사진-음성 정합성과 기기 저장 검증

현재의 `sessionId`, `audioOffsetMs`만으로 고정 몇 초를 잘라 설명을 붙이지 않는다.
말을 사진 전/도중/후에 시작할 수 있으며 한 설명에 사진이 두 장 들어갈 수도 있기 때문이다.

추가 설계 후보:

```text
점검 세션
  ├─ 촬영 이벤트: photoId, 촬영 시각, 현재 동호수 스냅샷
  ├─ 음성 타임라인: 발화 시작/끝, 원문, 변환 상태
  ├─ 위치 변경 이벤트: 유효 시각, 동호수, 확인 상태
  └─ 연결 결과: photoId ↔ segmentId, 연결 근거, 확인 필요 여부
```

녹음 타임라인과 촬영 이벤트의 기준 시간을 정하고 일시정지/재개/장치 중단을 반영한다.
사진 인접 발화를 후보로 찾되, 명확하지 않은 경우 `확인 필요`로 남긴다.
음성이 없던 사진에 이전 설명을 자동 복제하거나, 근거 없이 문장을 완성하지 않는다.
여러 사진=한 지적을 지원할지 먼저 정한 뒤 분리/병합 UI와 집계 단위를 설계한다.

기기 시험에는 세대당 30~40건 연속 촬영, 전화/앱 이동, 저전력, 권한 거부,
저장 공간 부족, 중간 새로고침, 세션 중단 복구를 포함한다.
지금의 가짜 미디어 자동 시험만으로 실제 휴대폰 녹음이 검증됐다고 판단하지 않는다.

## 3. 2단계: CLOVA 또는 검증된 음성 서비스 연결

CLOVA Speech를 우선 후보로 두되 연결 방식·지원 오디오 규격·현재 API 계약·요금은
개발자가 공식 문서와 테스트 계정에서 확인한 후 구현한다.
이번 패키지에는 키, SDK, 서버 프록시, 스트리밍 클라이언트가 없다.

권장 책임 분리:

```text
모바일 화면 → 인증된 자체 서버 → 음성인식 제공자
                         ↓
              원문·발화 시각·변환 상태 보관
                         ↓
              사진-발화 연결/위치 명령 처리
                         ↓
              등록 목록에 비동기 반영
```

브라우저에 제공자 비밀 키를 넣지 않는다. 제공자 요구 형식에 맞춘 오디오 변환,
업로드 또는 스트리밍, 실패/재시도, 부분 결과/확정 결과 처리를 서버 설계에 포함한다.
MediaRecorder Blob을 임의 조각으로 잘라 바로 요청하는 방식은 먼저 컨테이너 호환을 검증한다.

현장 용어 사전 후보는 알폼·갱폼·문선·코킹·퍼티·들뜸·단차·미시공 등과 실제 업체명이다.
사용 빈도와 실제 오인식 기록으로 관리하고, 현재 `TRADE_RULES`와 혼동하지 않는다.
원문과 교정문을 분리하며 동호수·수치·‘시공/미시공’ 등은 불확실할 때 추측해 바꾸지 않는다.

현장 문장 30~50개로 예비 비교하는 것은 시작점 제안이다.
본격 운영 전에는 소음/기기/발화자/공종별 평가를 넓혀야 한다.
문장 유창성보다 핵심 용어·업체명·동호수 오류 및 사람이 고치는 시간을 본다.

## 4. 3단계: 위치 음성 명령

‘위치 변경, 101동 1204호’를 지적 문장과 구분하여 처리한다.
동호수를 화면 상단에 크게 유지하고 변경되었음을 보여준다.
새 위치는 유효 시각 이후 촬영에만 적용하며 이전 기록은 자동 변경하지 않는다.
문장 중 업체명/호수 추정이 불확실하면 기존 위치를 유지하고 확인 대기 항목으로 남긴다.
수동 변경은 예외 처리로 계속 제공하되 매 사진마다 사용하게 만들지 않는다.

## 5. 4단계: 클라우드·공유

현장/사용자/권한 데이터가 현재 없으므로 서버 연동 전에 정의해야 한다.
필수 작업은 인증, 현장 접근권한, 사진/오디오 저장, 메타데이터 DB,
업로드 큐, 중복 등록 방지, 실패 재시도, 삭제/보관기간 처리다.
촬영 당시 생성한 ID를 서버에도 유지해 재전송이 새 기록을 만들지 않도록 한다.

제안 상태 흐름은 `로컬 저장 → 전송 대기 → 업로드 중 → 서버 확인 완료 / 실패`다.
이는 현재 코드의 구현 상태가 아니라 향후 추가할 상태 머신 제안이다.
STT 성공/실패와 파일 업로드 성공/실패는 별도 필드로 관리한다.
사용자가 수정한 설명을 늦게 도착한 STT 결과로 덮어쓰지 않는 버전 관리가 필요하다.

엑셀 생성은 소량일 때 현재 클라이언트 함수를 활용할 수 있다.
대량 데이터에서는 서버 내보내기/작업 큐를 검토하되 처리 결과가 실제 완료되었을 때 제공한다.

## 6. 5단계: 집계 품질을 먼저 만들고 AI를 추가

현재 통계는 등록된 지적 건수다. 미래 예측을 위해서는 최소한 다음 구조를 논의한다.

| 필요한 데이터 | 이유 |
| --- | --- |
| 전체 점검 대상·점검 이력·정상 결과 | 등록량과 발생률을 구분할 분모 |
| 독립 지적 ID, 사진/재점검 연결 | 같은 하자의 중복 집계 방지 |
| 공종/위치/유형의 표준 분류 | 서로 다른 표기를 동일 조건으로 비교 |
| 시공/점검 날짜와 공정 조건 | 어떤 시점의 정보로 예측했는지 구분 |
| 업체/자재/조건 등 합의된 변수 | 실제 현장의 조건 차이 설명 |
| 조치 이력·후속 발생 여부 | 미래 결과를 확인할 평가 기준 |
| 모델/데이터 버전·수정 이력 | 결과 재현과 변경 추적 |

AI 문구를 붙이기 전에 시간 순서/현장 분리 평가, 정상 사례 포함 여부,
중복/재점검 누출을 점검한다. 빈도 높은 순서만으로 미래 확률이라고 표시하지 않는다.
데이터가 부족한 조건은 예측을 숨기거나 ‘근거 부족’으로 표시한다.
모델 출력에는 대상 조건, 관측 기간, 근거 건수, 한계를 함께 표시하는 방향이 적합하다.
현재의 ‘발생 가능성 높음’ 시안에는 실제 결과 아님 표시를 유지한다.

## 7. 운영 전 점검

실제 현장 사진/음성의 저장·전송·공유·삭제 범위는 조직 정책에 맞게 확정한다.
다른 작업자의 음성이 함께 들어갈 수 있으므로 녹음 중 표시와 일시정지 수단을 유지한다.
데이터를 외부 학습 용도로 사용한다는 가정을 하지 않는다.
원문 보존, 수정 이력, 담당자 확인을 두고 자동 분석이 현장 확인을 대체하지 않게 한다.
